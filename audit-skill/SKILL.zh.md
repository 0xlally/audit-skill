# Audit Skill

英文主版本见 `SKILL.md`。

## 任务目标

审核已有漏洞候选，让通过审核的报告尽可能可以直接经受维护者、赏金平台 triager、CNA 或 CVE 审核。

不要挖掘新漏洞。如果用户只给了仓库、没有给候选漏洞、报告或 PoC，应要求用户提供要审核的候选。只为了验证提交声明，才阅读候选附近的代码。

默认所有候选都是未确认。只有通过证据、可达性、攻击模型、影响证明、重复/既有说明和严重性闸门后，才能建议提交。这个 skill 的默认偏向不是悲观，而是提交质量。

最终结论：

- `可提交`：证据充分、严重性可辩护、驳回风险已处理，报告可以提交。
- `提交前需修改`：问题可能真实或已经真实，但表述、证据、复现、影响范围或 CVSS 需要先修正。
- `需要验证`：漏洞可能成立，但缺少关键运行时、版本或影响证据。
- `降级`：问题真实，但原始严重性或影响被夸大。
- `拒绝`：误报、重复、预期/文档行为、不在范围内，或没有安全影响。

## 不可妥协规则

- 不得编造缺失证据，不得把假设写成事实。
- 没有 `E3` 不得标为 Confirmed High；没有 `E4` 不得标为 Confirmed Critical。
- 影响版本、默认/常见配置、攻击者可控 source、真实可达路径、已证明影响、重复/修复状态、CVSS 向量中任一关键项未知时，不得标为 `可提交`。
- 不得为了达到目标分数提高严重性。必须从已验证攻击模型和实际影响重新计算严重性。
- 除非用户明确要求修复，不得修改目标项目源码。

## 审核闸门工作流

按顺序执行闸门。只要确认存在阻断性驳回理由，就可以提前停止；否则保留简洁审核轨迹。

1. 接收候选并冻结原始声明。
   - 记录提交者原始声明：标题、受影响项目/版本/commit、组件、入口点、source、sink、信任边界、前置条件、声称影响、PoC、证据、声称 CVSS/CWE、计划提交渠道。
   - 区分事实和作者假设。摘录或概括原始严重性声明，确保之后的降级或修改是显式的。
   - 如果候选信息不足，列出缺失字段，并只能继续作为 `需要验证` 处理。

2. 证据底线。
   - 为每个候选标注 `E0` 到 `E4` 证据等级。
   - 静态代码审查、grep 命中、危险函数存在或 CodeQL 告警本身不足以提交。
   - 验证测试环境：准确 commit/tag、依赖版本、配置、功能开关、平台、认证状态，以及该环境是否等同于默认或常见部署。
   - 记录 PoC 是否最小化、非破坏、可复现，并且能因果证明声称影响。

3. 可达性与屏障检查。
   - 确认入口点真实存在、默认启用、在声称网络位置下可达，且不是测试代码、debug 路由、本地工具、管理员面板或内部 harness；若是，必须作为前置条件写明。
   - 沿 source 到 sink 复核认证、授权、租户隔离、解析逻辑、sanitizer、allowlist、escape、归一化、类型校验和其他 barrier。
   - 如果存在 barrier，判断它是完全阻断利用、缩小影响范围、改变前置条件，还是只部分缓解。
   - 对图模式或 CodeQL 证据必须人工复核。查询命中只是待检查路径，不是漏洞证据。

4. 攻击模型校验。
   - 证明攻击者如何控制 source。不得默认攻击者能控制 privileged browser context、本地服务、管理员页面、测试 harness、第三方 origin 或部署内部状态。
   - 从实际证明的路径确认 `AV`、`AC`、`PR`、`UI`，不要从想要的分数倒推。
   - 如果 source 控制依赖另一个漏洞、恶意 CDN、供应链污染、浏览器插件、社工、用户粘贴代码、非默认配置或可信管理员操作，必须显式写入前置条件并调整严重性。

5. 影响证明矩阵。
   - 每个声称的高影响维度都必须有具体证据。
   - `C:H`：实际读取了什么非公开敏感数据？属于哪个账号/租户？是否可复用？
   - `I:H`：实际修改了什么高价值状态？是否越权、持久并跨越安全边界？
   - `A:H`：实际造成了什么服务不可用、数据删除、崩溃、资源耗尽或核心功能不可用？
   - `S:C`：具体跨越了哪个安全边界？从哪个安全主体影响到哪个其他主体？
   - 函数名、schema、controller、registry、sink 或“可能导致”表述，本身不足以证明 High 影响。

6. 维护者驳回模拟器。
   - 先写出维护者最可能提出的最强驳回理由，再用证据尝试反驳。
   - 如果行为是文档说明、设计如此、已披露、已在受支持版本修复、依赖可信管理员、依赖用户自选不安全部署、重复已知问题、只影响 EOL/不支持版本、仅存在于测试/示例代码、由第三方误用导致，或影响太低，应拒绝或降级。
   - 网络可用时，搜索官方文档、安全策略、advisory、GitHub Security Advisory、NVD/CVE、changelog、release note、commit、issue 和赏金范围。
   - 如果无法反驳驳回理由，不得按原声明提交。

7. 严重性与表述审核。
   - 根据已验证事实重新计算 CVSS v3.1 或 v4.0。存在多个合理解释时，采用最低可辩护向量。
   - High 需要建议 CVSS >= 7.0 且证据等级达到 `E3`；Critical 需要建议 CVSS >= 9.0 且证据等级达到 `E4`。
   - CVSS 门槛只是必要条件，不是充分条件。实际影响必须匹配标签。
   - 将投机表述改成克制表述：只有已证明时写“允许/导致”，未确认路径写“可能”，没有证明系统级影响时不得使用系统级措辞。

8. 提交包。
   - 对 `可提交` 结论，使用 `template/finding-template.zh.md` 产出面向维护者的报告，包含准确版本、前置条件、复现、证据、影响、CVSS/CWE、修复建议、重复检查和披露渠道。
   - 对非可提交结论，输出阻断缺口，以及让候选变得可审核所需的最小证据或措辞修改。
   - 保持 payload 安全，并脱敏真实密钥、生产令牌、私有用户数据和破坏性细节。

## 证据等级

每个候选必须有一个证据等级：

- `E0`：仅关键词/规则命中、危险 API、可疑模式或未复核告警。不得提交。
- `E1`：静态 source-to-sink 路径看似可行，但入口、配置、权限或运行时行为未验证。最高只能是 `Possible`。
- `E2`：本地/测试验证到达 sink，但默认配置、前置条件或安全影响不完整。通常只能 `需要验证` 或 `降级`。
- `E3`：默认或常见配置下，用非破坏 PoC 证明完整攻击链和明确安全影响。Confirmed High 的必要条件。
- `E4`：默认或常见配置下，证明低复杂度即可造成系统级、跨租户、控制面、密钥/凭据、账号接管或大规模数据妥协。Confirmed Critical 的必要条件。

没有 `E3`，不得写 Confirmed High。没有 `E4`，不得写 Confirmed Critical。

## 输出规则

先给结论和一句话理由。

多个候选时按 `可提交`、`提交前需修改`、`需要验证`、`已降级`、`已拒绝` 分组。

每个候选使用精简卡片：

- 标题和结论
- 原始严重性 vs 审核后严重性
- 证据等级
- 受影响版本/组件
- 攻击模型和前置条件
- 已验证影响
- 关键证据或缺失证据
- 维护者驳回风险
- 必要下一步

只有当发现为 `可提交` 或用户要求提交草稿时，才使用 `template/finding-template.zh.md` 创建完整报告。
